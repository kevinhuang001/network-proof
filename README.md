# NetProof Wallet

用一台**永久断网的旧安卓手机**做硬件钱包，配一个**伴侣钱包**（网页版，也提供 Chrome 扩展构建）做日常观察与签名入口。
私钥从摄像头传感器的物理噪声生成，永不离开手机；一切签名通过**二维码气隙**往返。

已构建好的 APK 在 [`artifacts/`](artifacts/)：`netproof-air-0.1.0.apk`（release，3.3 MB，已签名，**无 INTERNET 权限**）。

```
┌──────────────────────────────┐                    ┌───────────────────────────┐
│  NetProof Air（离线手机）      │                    │  NetProof Companion        │
│  Capacitor + Web 技术         │   ── NP-XPUB ──▶   │  网页版（推荐）             │
│  安卓 APK                     │      扫码登录        │  Chrome MV3 扩展（可选）    │
│                              │                    │                           │
│  • 摄像头噪声 → 真随机数        │                    │  • 只有 xpub，没有私钥       │
│  • BIP39 助记词 + passphrase  │   ◀── NP-REQ ──    │  • 通过 RPC 读链上数据       │
│  • Argon2id 加密保管           │      签名请求        │  • 本地交易历史             │
│  • 屏幕显示待签内容并签名        │   ── NP-SIG ──▶   │  • 收到签名后校验并广播       │
└──────────────────────────────┘                    └───────────────────────────┘
            飞行模式 · 无网络权限 · 无 INTERNET permission
```

伴侣钱包有两种形态，共用同一个策略层 `@netproof/companion`：

| | 网页版（`apps/companion-web`） | Chrome 扩展（`apps/extension`） |
|---|---|---|
| dApp 自动发现 | ✗ 不能注入 `window.ethereum` | ✓ EIP-1193 + EIP-6963 |
| 内置 dApp 测试台 | ✗（已删） | ✗ |
| 存储位置 | 页面 origin 的 `localStorage` | `chrome.storage.local`（与页面隔离） |
| 私钥 | 没有 | 没有 |

网页版是原型阶段推荐的使用方式：不需要加载未打包扩展，发送流程就能完整演示气隙往返。

> 伴侣钱包里原来的「dApp 测试台」已经删掉了。它是个开发工具，却占据着产品设置的入口；
> 想直接对链发 JSON-RPC 或构造任意签名请求，用 `pnpm dev:extension` 加载扩展，或临时在
> `apps/companion-web/src/screens/` 下加回一个页面。

## 为什么这样设计

**私钥不在浏览器里。** 插件保存的全部内容是 xpub（扩展公钥）。浏览器被完全攻破，攻击者也只能"看"和"请求签名"，
不能自己签。这是与 MetaMask 等热钱包最根本的区别，也是这个项目存在的理由。

**随机数来自物理世界。** 不用软件随机数生成助记词。手机摄像头对准任何有光的地方，逐帧比较像素差异——
差异里剩下的是读出噪声、散粒噪声和 ADC 抖动。攻击者无法预测或复现传感器的热噪声。

**气隙是操作系统保证的，不是承诺。** Android 清单里**没有** `INTERNET` 权限，页面 CSP 禁止外连，
网络配置拒绝明文传输。离线不是"我们不会联网"，而是"联不上网"。

设备界面显示的**不是**程序检测出来的"你联网了"，而是可以被你独立验证的事实：
APK 未声明 `android.permission.INTERNET`——你可以用
`aapt2 dump permissions netproof-air-0.1.0.apk` 自己核对。设备也申请了 `CAMERA`，
仅此而已（早先版本还申请 `ACCESS_NETWORK_STATE` 用来判断飞行模式；那个功能已经删掉，
权限也一并删掉，不再持有无用途的权限）。

程序无法可靠地替你判断是否断网，所以它不假装能判断，也不提示你开飞行模式。

**设备上显示什么，就签什么。** 离线设备独立解码交易、展示解析后的调用内容与风险提示，再从**显示过的字段**
重新序列化并签名。插件随后用同一个哈希独立校验签名。

### 旧手机兼容性

目标是**永久断网的旧安卓手机**：它不会联网，所以永远收不到 Play 商店的 WebView 更新，
WebView 版本停在出厂状态。构建下限因此是 **WebView 67**——再低就没有 `BigInt`，
而钱包的全部金额运算都靠它，且 `BigInt` 没有 polyfill。

比 67 新的语法由 esbuild 降级，运行时 API 由 `apps/hardware/public/compat.js`（ES5 经典脚本，
在 bundle 之前加载）补齐，flexbox `gap` 与 `aspect-ratio` 这类无法打补丁的 CSS 特性在运行时探测后走
降级规则。完整清单与验证方式见 [`docs/COMPAT.md`](docs/COMPAT.md)。

## 使用流程

**1. 在离线手机上创建钱包**

飞行模式 → 在首页确认「网络状态」与「飞行模式已确认」→ 创建新钱包 → 对准有光的地方采集 3–5 秒（进度条显示的是**保守估算的熵比特数**，
不是时间）→ 抄写助记词并通过抽查 → 可选设置 BIP39 passphrase → 设置设备密码。

采集过程中屏幕会实时显示：累计帧数、原始比特数、以及熵是否在增长。如果画面静止、镜头被遮挡、
或者手机相机的预览管线开了降噪，进度条会停住并给出提示——设备**宁愿拒绝创建钱包，也不会生成一个弱助记词**。

**2. 导出 xpub（扫码登录）：只有扫码这一条路**

设备显示动画二维码，插件用摄像头扫描它——配对方式**只有扫码**，没有手动导出、粘贴 xpub 之类的旁路。
理由很简单：扫到的就是这台设备的真实 xpub，少一条"用户手抄/粘贴"的路径，就少一类"扫错了/粘错了"的事故。

**3. 账户与派生**

一个钱包从来不止一个地址：仅 `m/44'/60'/0'` 就能派生无限个收款地址，资金经常散在多个账户里。
伴侣钱包按"钱包 → 账户"两级组织，和 MetaMask 一样：

- **钱包**是设备（一个助记词、一个指纹），可以有多个，各自记着自己的账户选择；
- **账户**就是 `m/44'/60'/0'/0/i`，从设备导出的**那一个** xpub 推导出来，**数量不限**——
  「添加账户」是本地操作，不需要设备参与，也没有"用完"这回事。

设备只导出 BIP44 一个方案（`m/44'/60'/0'`）。Ledger Live 的账户模型和 MyEtherWallet 的老链式路径
都已经删掉：它们唯一的作用是让恢复助记词的人看到一个自己**不认识**的地址，而这一步的全部意义
恰恰是证明"我认识它"。

手机上点「登录插件钱包」→ 显示动画二维码 → 插件里点「添加钱包」→ 用电脑摄像头扫描，
然后给它起个名字。插件拿到的是**一个** BIP44 账户级 xpub（`m/44'/60'/0'`）加设备派生的 Solana 地址。

**Solana 是唯一有上限的**：它的路径全是硬化的（SLIP-0010），公钥推不出新地址，所以插件只能显示
设备算出来的那些（设备端默认 5 个，可在设备「设置」里调）。已显示的账户数超过设备导出数量时，
插件会拒绝切到 Solana 并提示重新导入，而不是默默少显示几个。

默认只导出账户级 xpub；可选导出根 xpub（插件就能派生任意路径，但也会看到你所有账户的地址）。

**3. 连接 dApp**

插件注入了 `window.ethereum`（EIP-1193）并通过 **EIP-6963** 广播自己，所以现代 dApp 能自动发现它。
只读调用（余额、nonce、gas、`eth_call`…）直接转发给你配置的 RPC 节点；任何需要私钥的调用都会
变成一次待批准请求，打开一个扩展标签页。

**4. 签名**

流程是两段扫码：

1. 插件标签页显示**签名请求**的动画二维码，同时打开摄像头；
2. 手机扫它 → 独立解析并展示：金额、收款方、网络、Gas、以及**调用解析**
   （`transfer` / `approve` / `setApprovalForAll`…），无限授权这类高风险操作会标红；
3. 手机上确认（如果启用了 passphrase，需要输入）→ 手机显示**签名结果**二维码；
4. 伴侣钱包扫回来 → 校验三件事 → 自动广播或把签名交还 dApp。

校验的三件事（任何一项不过都会拒绝，不会广播）：
- 响应里的请求 ID 与 `claim` 哈希与你发出的请求一致；
- 签名能恢复出你批准的那个账户；
- 签名载荷与你确认过的字段**逐字节相同**。

## 项目结构

```
packages/core        纯 TypeScript 引擎，零平台依赖（Node / WebView / Service Worker 都能跑）
  src/entropy/       摄像头噪声提取、NIST SP 800-22 风格健康检验、熵估算
  src/crypto/        BIP39 / BIP32 / BIP44、EVM 签名、交易解码与风险提示
  src/qr/            CBOR 编解码、LT 喷泉码、帧格式、气隙协议
  src/vault/         Argon2id + XChaCha20-Poly1305 加密保管库
packages/companion   伴侣钱包策略层：EIP-1193 方法分类、节点访问、xpub 地址推导（无框架）
packages/ui          OKX 风格设计令牌与组件 CSS（所有前端共用）
apps/hardware        NetProof Air — Capacitor 安卓硬件钱包（APK）
apps/companion-web   NetProof Companion 网页版（推荐）
apps/extension       NetProof Companion Chrome 扩展（可选，含 EIP-1193 provider）
scripts/build-apk.sh 一键装工具链 + 构建 + 验证 APK
```

`packages/companion` 被两个伴侣形态共用，所以"签名方法只能变成待批准请求、绝不本地签名"
这条规则不可能在网页版为真、在扩展里为假。

`packages/core` 里**没有任何**网络、文件系统或平台 API 调用，所以同一份代码在三个环境里行为一致，
也是它能在 Node 里被完整测试的原因。

## 真随机数是怎么来的（以及它有多诚实）

这是整个项目最需要被审视的部分，所以把机制和它的局限都写清楚。

**提取。** 静态场景下，相邻两帧的同一像素本应完全一致，差异来自传感器噪声。提取器有两种模式：

- **模式 B（读出噪声）**：`|差值| ≥ 2` 的像素，取其**中位数中心化后差值的符号**。
  减去中位数是为了消除自动曝光带来的整体漂移——否则所有符号都会相同。
- **模式 A（量化抖动）**：当传感器噪声小于 1 个 ADC 码时，模式 B 什么也提不出来（大部分差值为 0）。
  这时改用三帧窗口：对**始终安静**（两步差值都 ≤ 1）的像素取 `(v[t] ^ v[t-2]) & 1`。
  离量化边界远的像素永远输出 0，这些会被去偏置丢弃，**不会**被当成随机数。

一步 **von Neumann 去偏置**（`01→0`、`10→1`，相同则丢弃）消除残余偏置。

**去偏置是跨时间配对的，不是跨空间。** von Neumann 去偏置要求每个比特对里的两个比特独立。
相邻像素**不**独立（读出噪声的行/列偏移、PRNU、镜头模糊让它们同涨同落），所以早期版本按像素顺序
配对，把绝大部分熵当成"相同对"丢弃了。现在每个像素与**它自己在上一帧**的比特配对——
跨时间才是独立性成立的地方。实测在同一传感器模型下可提取比特数量提高约 **2.8 倍**。

**熵是怎么算的。** 不是"采了多久算多少比特"，而是：

```
credit = 该模式的有效比特数 × 实测最小熵/比特 × 0.05
```

`实测最小熵/比特` 由该模式输出流中 1 的比例推出（`-log₂(max(p, 1-p))`，即 NIST SP 800-90B 的
MCV 估计思路）。所以模式 A 在一个"干净"传感器上输出几乎全是 0 时，`p ≈ 1`，credited ≈ 0——
**设备会拒绝创建钱包，而不是凭空生成一个弱助记词**。

最后的 `0.05` 折扣是刻意保守的：它代表我们无法从一次采样中证明的**空间/时间独立性**。
换句话说，我们假定 20 个提取出的比特里最多只有 1 个是真正独立且不可预测的。

**健康检验，以及它曾经怎么把产品弄坏。** 生成助记词之前会跑 NIST SP 800-22 风格的检验。
这里有三个必须说清楚的坑，我们全部踩过一遍：

1. **检验的对象必须是近似 i.i.d. 的样本。** 去偏置后的比特流在**空间上**是相关的（这是真实传感器的
   正常现象，不是故障）。直接对它跑 runs/块频率/序列相关，在一台完全健康的设备上也会 p = 0 全灭。
   所以采集器另外构造一份**抽样样本**：每个槽位每隔一帧取一个比特（见下一条），再拼接起来检验。
2. **样本大小必须固定。** 固定 α 的假设检验随着样本增大必然拒绝——同一个健康传感器，采 40 帧通过、
   采 300 帧失败。样本大小现在固定为 64 槽 × 128 帧，结论不再随"用户举着手机多久"漂移。
3. **"数据不足"不等于"失败"。** 样本太小导致检验无法判定时，报告为 `inconclusive`（界面显示"数据不足"），
   而不是当成失败——否则最短的合法采集永远无法完成。

另外，序列相关检验只作为**提示**（advisory）：它最容易对合法传感器行为报警，而熵的结论来自实测折扣，
不来自 p 值。所有这些数字（含审计摘要与"数据不足"项）都能在设备「设置与自检」里看到。

**诚实的局限：**

- 熵估算基于一个保守启发式模型，**不是**经过认证的熵源评估。真要用于保护大额资产，应该做一次
  NIST SP 800-90B 的完整评估。
- 手机相机预览管线可能做时域降噪。这会让可提取熵暴跌——设备会因此拒绝创建钱包，这是**正确的
  失败方式**，但也意味着某些机型需要对着更暗/更有纹理的区域采集。
- JS 无法保证内存擦除。助记词在解锁期间以字符串形式存在于内存中；`lock()` 会丢掉引用，但
  精确的擦除做不到（这是所有基于 JS 的钱包共同的限制）。
- 「自检」用合成噪声验证管线，它证明**代码**在这台设备上正确工作，不证明**传感器**的熵。
  传感器的证据是采集界面上那个实测比特数。

## passphrase

BIP39 passphrase（"第 25 个词"）与助记词一起推导出**完全不同的钱包**。

- 它保护的是"助记词被看到"的场景：只拿到 24 个词的人，没有 passphrase 打不开你的资产。
- 它**没有校验位、没有提示、无法找回**。丢了就是丢了。
- **它不是一个"加在助记词上的密码"，而是另一个钱包。** `(助记词, passphrase)` 一起推导出地址；
  同一串助记词配上不同 passphrase 就是两个互不相干的钱包。所以"不带 passphrase 的那个"本身也是一个
  可用账户（常被当作诱饵账户），设备会明确告诉你当前显示的是哪一个。
- **passphrase 会与助记词一起加密保存在设备上**（不是一个可选项）。解锁后签名自动使用，
  不需要每次重新输入。

  > 这是一个明确的产品决策，代价必须写清楚：**两者由同一个设备密码保护**。
  > 设备被解锁、或设备密码被猜到/暴力破解，助记词与 passphrase 会**同时暴露**，
  > passphrase 就不再是独立的第二因子。请把设备密码当成唯一的防线来保管，
  > 使用足够长且唯一的密码。
  >
  > 如果你以后想让 passphrase 重新成为独立因子（每次签名手动输入），
  > 改动点在 `apps/hardware/src/state/session.tsx` 的 `persist()`：不再写入 `passphrase` 字段即可。

- 设备另外只保存一个**非机密**事实："这个钱包启用了 passphrase"。所以万一 passphrase 没能载入，
  它会在解锁时明确警告"你正在进入**不带 passphrase 的那个钱包**"，而不是让你以为钱包变了。
- 设备在解锁与签名时都会明确提示当前是否载入了 passphrase——因为**签名会来自另一个钱包**，
  而不只是"签名失败"。

## 二维码传输为什么不只是"把数据放进二维码"

一笔带 calldata 的 EIP-1559 交易序列化后轻松超过 1KB，远超单个二维码的可靠容量，
所以采用**动画多帧二维码 + LT 喷泉码**：

- 发送方每帧 XOR 若干个分片，帧编号 `i` 对应的分片组合是
  `(消息摘要, 分片数, i)` 的**纯函数**——双方不需要任何额外信道，接收方也不需要记住发送进度。
- 接收方需要的是**任意**约 k 个分片，不要求顺序、不要求不重复。摄像头漏帧、重帧、抖动都无所谓，
  这正是"举着手机对准屏幕"能真正用起来的原因。
- 每帧带 CRC-32（立即丢弃误读）和 4 字节消息摘要前缀（识别并忽略其他传输）。
- 分片大小可调（稳健 200B / 均衡 300B / 快速 500B）。

端到端测试会真的把帧渲染成**像素**，再用 jsQR 解回来（`test/qr-e2e.test.ts`），
所以"帧太长导致扫不出来"这类问题是测试能发现的，而不是用户发现的。

## 测试

```bash
pnpm test        # core 177 · companion 29 · companion-web 8 · extension 6 · hardware 11
```

测试的重点不是覆盖率，而是**用独立实现交叉验证**：

| 测试 | 验证方式 |
|---|---|
| BIP39 | 官方 Trezor 向量（含 `TREZOR` passphrase 的完整种子） |
| BIP32/BIP44 | 与 **ethers v6** 逐地址比对（BIP44 / Ledger Live / legacy 路径） |
| EVM 地址 | 硬编码的私钥→地址向量（`0x…01 → 0x7E5F…5Bdf`） |
| EIP-1559 签名 | 与 ethers 逐字节相同（含 RFC 6979 确定性 nonce 与 low-S） |
| EIP-191 / EIP-712 | 用 ethers 的 `verifyMessage` / `verifyTypedData` 验证 |
| CBOR | RFC 8949 规范中的示例字节序列 |
| 喷泉码 | 乱序 + 重复 + 丢帧下重建 5KB 载荷 |
| 二维码 | 真实像素 → jsQR 解码 → 喷泉解码 → 消息 |
| 熵提取 | 合成高斯噪声帧；遮镜头/静止画面/低熵必须**拒绝**创建钱包 |
| 保管库 | 错误密码、密文篡改、**KDF 参数降级**都必须失败 |
| dApp 策略 | 未授权站点拿不到账户、签名方法只能变成待批准请求、金额/地址校验 |
| 伴侣存储 | xpub 往返正确；**断言存储里不含 mnemonic/私钥/xprv**；设置合并不丢默认值 |
| 离线状态展示 | 不得把平台的猜测说成事实：`online` 必须标注来源并披露权限失效模式 |
| 助记词导入 | 逐词定位拼错并给建议；区分"词表外"与"校验位不符"；容错换行/全角空格/大小写 |
| 多账户派生 | 已导出账户全部可枚举并各自派生独立地址；**未导出的账户必须为空**（硬化密钥推不出来） |
| 地址数量上界 | 每个账户的派生数量有硬上限，配置写错也不会触发海量派生 |
| UI 不变量 | `.np-blur` 不得禁用交互；任何 input/textarea 不得带 `np-blur`（防止"输入框点不动"复现） |
| 真实传感器熵 | 跨时间配对必须比跨空间多出 >1.5 倍熵；11 种采集参数全部能完成；长时间采集不得被拒绝 |
| 退化源必须拒绝 | 冻结画面、确定性周期图案都必须失败；两码抖动是**真随机**，允许通过但要求保守折扣 |

最后一条值得强调：`packages/core` 里刻意**没有**"本地签名"这种兜底路径——不是没实现，是不存在。

## 安全模型与已知限制

**这个原型级实现有意没有做的：**

- **没有安全芯片。** 私钥在应用处理器上运算，不是智能卡。真实产品应该用 StrongBox / secure element。
- **保管库存在 WebView 的 `localStorage`**，用 Argon2id + XChaCha20-Poly1305 加密。
  接口（`apps/hardware/src/lib/storage.ts`）刻意做窄，方便换成 Android Keystore 支持的插件。
- **没有交易模拟。** 展示的是解码后的调用参数，不是模拟结果。看不懂的合约调用只会提示"无法识别"。
- **没有多签、没有 PSBT、只有 EVM。** 比特币、Solana 等未实现（协议是可扩展的）。
- **伴侣钱包对 dApp 只暴露 EVM 方法**，`wallet_addEthereumChain` 被明确拒绝——网络由用户配置，
  不由网站提供（否则 dApp 可以把你指向一个它控制的 RPC，进而操纵 nonce/gas/链 ID）。
- **服务 worker 可以被 Chrome 随时停止。** 待签请求持久化在 `chrome.storage.local`，
  但等待中的 Promise 在内存里；页面一直开着时端口会保活 worker。生产版本需要一套重连协议。
- **网页版把 xpub 放在 `localStorage`**，而那个 origin 也是你访问 dApp 的地方。
  上限是隐私而非资产（见 `docs/SECURITY.md` §4.11）。
- **APK 只做了构建期验证**（权限、签名、清单加固），没有在真机上启动过。
- **系统报告的网络状态可能是错的。** 它只能用作提示；真正的保证是缺少 INTERNET 权限。
- **助记词恢复（导入）流程**没有走摄像头熵采集，导入的助记词来自用户，设备只能提示风险。
