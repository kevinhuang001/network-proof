# 气隙协议规范 v1

本文档描述 NetProof Air（离线设备）与 NetProof Companion（Chrome 插件）之间通过二维码传输的线格式。
实现位于 [`packages/core/src/qr/`](../packages/core/src/qr/)。

协议的目标不是"通用"或"优雅"，而是**在人手举着手机对准屏幕的不稳定光学信道上不出错**，
同时让接收方能够证明自己解出来的就是发送方发出去的。

---

## 1. 分层

```
消息 (Message)           CBOR map，见 §5
   │  encodeCbor
   ▼
载荷 (Payload)           uint8 数组，长度 ≤ 65535
   │  FountainEncoder
   ▼
分片 + 帧 (Frame)        每帧 = 摘要(4) ‖ 长度(2) ‖ CRC(4) ‖ 分片数据(N)
   │  base32 + 文本头
   ▼
二维码字符串              NP1:<TYPE>:<seq>-<count>:<BASE32>
   │  qrcode 渲染 / jsQR 解码
   ▼
像素
```

接收方向完全对称：解码二维码字符串 → 校验 CRC → 交给喷泉解码器 → 载荷 → CBOR → 消息。

---

## 2. 二维码字符串格式

```
NP1:NP-XPUB:3-12:AEBAGBAF...
 │    │      │  │   └─ base32(RFC 4648, 大写, 无填充) 的帧二进制
 │    │      │  └───── 分片总数 (fragmentCount)
 │    │      └──────── 帧序号 (seqNum, 从 0 开始, 无上限)
 │    └─────────────── 消息类型
 └──────────────────── 固定魔数 + 版本
```

**为什么是 base32。** QR 的 alphanumeric 模式每字符 5.5 bit，byte 模式 8 bit。
base32 把 N 字节变成 1.6N 个字符，走 alphanumeric 模式的有效密度是 1.6N × 5.5 = 8.8N bit；
base64 走 byte 模式是 1.33N × 8 = 10.7N bit——**base64 其实更紧凑**，但 alphanumeric 模式下
同样的 QR 版本能容纳的**字符数**更多（4296 vs 2953），换算到载荷是 2685 字节 vs 2214 字节。
另外 `NP1:` `:` `-` 全部落在 alphanumeric 字符集内，整个字符串可以用一个模式编码。

**消息类型：**

| 类型 | 方向 | 用途 |
|---|---|---|
| `NP-XPUB` | 设备 → 插件 | 导出观察钱包（扫码登录） |
| `NP-REQ` | 插件 → 设备 | 签名请求 |
| `NP-SIG` | 设备 → 插件 | 签名结果 |
| `NP-ACK` | 双向 | 回执 / 错误 |

## 3. 帧二进制布局

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 4 | `digestPrefix`：`sha256(payload)[0..4)` |
| 4 | 2 | `messageLength`：载荷原始长度，大端 uint16 |
| 6 | 4 | `crc32(digestPrefix ‖ messageLength ‖ fragment)`，大端 |
| 10 | N | 分片数据（XOR 组合结果） |

**`messageLength` 必须在每个帧里重复**，因为喷泉码的最后一帧是按分片长度零填充的，
接收方需要知道裁掉多少。

**`digestPrefix` 必须重复**，因为它是喷泉码编码方案的随机种子（见 §4），
接收方在看到第一帧时就要能复现出后续所有帧的分片组合，而不能等到解码完成。

**CRC 在校验之前**。误读的二维码（反光、模糊、半帧）必须立刻丢弃，
绝不能让它污染解码器状态。

## 4. LT 喷泉码

### 动机

顺序多帧协议要求收到每一帧且顺序正确。手持摄像头会漏帧、重帧、抖动，
所以需要一种**无速率（rateless）**编码：接收方收到任意约 k 个分片即可完成，
不关心顺序、不关心重复。

### 编码方案是纯函数

```
indices(i) = chooseFragments(i, k, digestPrefix)
```

给定 `(帧序号, 分片数, 摘要前缀)`，帧 `i` XOR 了哪些分片是完全确定的：

1. 用 `Prng`（SHA-256 计数器模式，种子 = `digestPrefix ‖ uint32be(i)`）取一个度 `d`；
2. 从鲁棒孤子分布（robust soliton，`c = 0.1`, `δ = 0.5`）采样 `d`；
3. 用拒绝采样取 `d` 个**互不相同**的分片下标。

因此：

- 发送方不需要保存任何状态，可以无限循环帧序列；
- 接收方不需要知道发送进度，也不需要按顺序扫描；
- 两边不可能"对编码方案理解不一致"，因为它是同一份纯函数。

`Prng.nextInt(n)` 用拒绝采样而不是取模，避免模偏置——一个带偏置的度分布会让喷泉码
永远收不齐最后几个分片。

### 解码

标准的剥离（peeling）解码：维护一组方程，每个方程是"若干未知分片的 XOR = 已知值"。
当一个方程只剩一个未知数时即可解出，并把该分片代入所有其它含它的方程。
实现用 `equationsByFragment` 索引，避免每次求解都遍历全部方程。

重复帧、属于其他传输的帧（摘要前缀不同）都会被静默忽略并计数。全部 k 个分片到齐后，
重新计算 `sha256(payload)[0..4)` 并与 `digestPrefix` 比对；不一致则**抛错而不是返回数据**。

### 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `fragmentLength` | 300 B | 每帧载荷字节数。200B 更稳健，500B 更快 |
| `frameCount` | `⌈k × 1.6⌉ + 3` | 生成的**不同**帧数（生成多于 k 是为了缓解"集齐优惠券"问题） |
| `frameDurationMs` | 420 ms | 动画帧间隔 |

一帧文本长度约 `1.6 × (N + 10) + 20` 字符。N=300 时约 516 字符，
在 QR 版本 ~19（纠错级别 M）内，用 320px 的显示宽度就能被另一台手机可靠读取。

## 5. CBOR 消息

编码规则（`packages/core/src/qr/cbor.ts`）：

- **确定性**：map 的键按编码后的字节序排序，所以同一逻辑消息永远产生同样的字节。
  这是 `claim` 哈希（§6）成立的前提。
- **只用整数**：禁止浮点。大于 2⁶⁴-1 的数值（EVM 的 uint256）用 32 字节大端字节串承载，
  见 `uint256ToBytes`。
- **拒绝而不是猜测**：不支持的类型（不定长、tag、非文本键）直接抛错。

### 5.1 `NP-XPUB` — 导出观察钱包

| 键 | 类型 | 说明 |
|---|---|---|
| `t` | text | `"xpub"` |
| `v` | uint | 协议版本，当前 `1` |
| `fp` | text | BIP32 主指纹（8 位十六进制） |
| `pw` | bool | 是否启用了 BIP39 passphrase |
| `root` | text | 根 xpub（默认等于账户 0 的 xpub，除非用户选择导出真正的根） |
| `ct` | uint | SLIP-44 币种，EVM 为 60 |
| `dev` | map | `{name, model}`，供用户辨认设备 |
| `sch` | array | 派生方案模板：`{id, label, xp, rcv, chg}` |
| `acc` | array | 账户级导出：`{a, s, xp, x, fa}` |

`sch` 里的模板是插件唯一需要知道的"路径知识"：

| id | xpubPath | receive | change |
|---|---|---|---|
| `bip44` | `m/44'/60'/{account}'` | `m/44'/60'/{account}'/0/{index}` | `m/44'/60'/{account}'/1/{index}` |
| `ledger-live` | `m/44'/60'/{account}'/0` | `…/0/{index}` | — |
| `legacy-mew` | `m/44'/60'/{account}'` | `m/44'/60'/{account}'/{index}` | — |

插件用这些模板从账户 xpub 派生地址，**不需要任何私钥**，也无法派生硬化子密钥。

### 5.2 `NP-REQ` — 签名请求

| 键 | 类型 | 说明 |
|---|---|---|
| `t` | text | `"req"` |
| `v` | uint | 版本 |
| `id` | bytes(16) | 随机关联 ID |
| `k` | text | `"tx"` \| `"msg"` \| `"typed"` |
| `p` | text | 派生路径，如 `m/44'/60'/0'/0/3` |
| `a` | text | 插件认为该路径对应的地址（设备会独立验证） |
| `c` | uint | chain id |
| `o` | text? | 请求来源 origin（dApp 场景） |
| `claim` | bytes(32) | 请求自身的哈希，见 §6 |
| `tx` | map? | `{ty, n, to, v, d, g, mf?, mp?, gp?}` |
| `msg` | map? | `{t: 文本, h?: 原始字节}` |
| `td` | map? | EIP-712：`{domain, types, primaryType, message}` |

`tx.to` 是**字节串**（空字节串表示合约部署），`tx.v`（value）是 32 字节大端。
链上数量一律用字节串而不是 CBOR 整数，是为了避免宽度歧义。

### 5.3 `NP-SIG` — 签名结果

| 键 | 类型 | 说明 |
|---|---|---|
| `t` | text | `"sig"` |
| `id` | bytes(16) | 回显请求 ID |
| `ok` | bool | 是否成功 |
| `k` | text | 与请求一致 |
| `a` | text | 实际签名的地址 |
| `claim` | bytes(32) | 回显请求的 claim |
| `dg` | bytes(32) | 设备实际签名的摘要 |
| `raw` | text? | 已签名交易（EIP-2718 十六进制） |
| `sig` | bytes(65)? | 消息签名（`r ‖ s ‖ v`，v = 27/28） |
| `err` | text? | 失败原因（用户可读） |

协议层强制：`ok = true` 时**必须**带 `raw` 或 `sig`，否则解码报错。
一个"成功但没有签名"的响应是协议违规，不能悄悄通过。

### 5.4 `NP-ACK`

`{t: "ack", v, id, ok, err?}` — 用于快速拒绝（例如用户取消、请求格式不支持）。

## 6. `claim`：请求绑定

```
claim = sha256("netproof/claim/v1" ‖ id ‖ kind ‖ canonicalCBOR(request with claim = 32×0x00))
```

构造时先用 32 个零字节占位，再把整个请求做规范 CBOR 编码并哈希。
验算时用收到的字段重建（同样用零占位）并比对。

**为什么需要它。** 插件与设备之间没有任何加密信道——二维码是公开可见的。
`claim` 让双方都能证明"我处理的正是对方发出的那一条消息"：

- 设备可以把 `claim` 显示在屏幕上，让用户比对（原型未做，接口已就绪）；
- 插件收到响应时必须校验 `claim`，否则无法区分"设备签了我的请求"和
  "有人把另一个签名结果塞进了我的摄像头视野"。

`claim` 依赖规范 CBOR：**相同的逻辑内容必须产生相同的字节**。这就是 §5 里
"map 键排序"和"禁止浮点"这两条硬性规定的原因。

## 7. 请求生命周期（dApp 签名）

```
dApp               插件 background          插件标签页            离线设备
 │ eth_sendTransaction
 ├──────────────────▶│
 │                   │ 建立 PendingRequest
 │                   │ 持久化 (chrome.storage.local)
 │                   ├──────────────────────▶│
 │                   │                       │ 补全 nonce/gas/fee（读 RPC）
 │                   │                       │ 构造 NP-REQ + claim
 │                   │                       │ 显示动画二维码
 │                   │                       ├────── NP-REQ ──────▶│
 │                   │                       │                      │ 独立解码 + 展示
 │                   │                       │                      │ 用户确认
 │                   │                       │◀───── NP-SIG ────────┤
 │                   │                       │ 校验 id/claim/地址/载荷
 │                   │                       │ 广播 eth_sendRawTransaction
 │◀──────────────────┤◀──────────────────────┤
 │  tx hash          │  approval-result
```

**只有 background 会广播交易**，标签页只负责校验并通过消息把结果交给 background。
这样"能触达网络的代码"只有一处，容易审计。

**补全发生在插件侧、QR 之前。** 设备离线，无法查询 nonce 或 gas 价格，
所以插件必须先把它们解析成确定值。解析不出来就明确失败——
硬件钱包签一个猜测的 nonce，等于签一笔错误的交易。

## 8. 版本与兼容性

- 版本字段是每个消息里的 `v`，当前为 `1`。版本不匹配时解码抛
  `PROTOCOL_INVALID`，双方都不会尝试"尽量兼容"。
- 帧魔数是 `NP1`。未来不兼容的帧布局会换成 `NP2`，这样旧设备会明确拒绝而不是误解。
- **本协议不是 BC-UR。** 设计目标与 Keystone / Foundation 的 UR 类似
  （喷泉码 + CBOR + 动画 QR），但帧格式、PRNG 和 CBOR schema 都是独立的，
  **两者不能互通**。选择自研是为了让帧格式可以用纯函数描述并且完全可测试；
  代价是放弃了与现有硬件钱包生态的互操作。

## 每帧多大：由载荷决定，不由档位决定

帧的密度（也就是二维码的模块数）是扫码成功率的主要变量，而它过去是一个固定值：每帧 300 字节。
实测下来，一笔签名请求（CBOR 315 字节）会变成 73×73 模块的码，xpub 导出（476 字节）也一样。

另一台手机要用摄像头分辨 73 个模块的每一格：480 像素的中间取景方形里放 73 格，约每格 4 像素，
而 jsQR 大致就从这里开始失败。所以发送方现在先量一次载荷，再挑一个**刚好放得下**的分片长度
（`chooseFragmentLength`，目标约 53 模块 / 每帧 236 字符），用户选的档位是**上限**：

| 载荷 | 每帧 | 帧数 | 模块 |
|---|---|---|---|
| 315B NP-REQ | 105B | 8 | 53 |
| 476B NP-XPUB | 119B | 10 | 53 |
| 旧行为（固定 300B） | 300B | 7 | **73** |

代价是多一帧、约 420 毫秒；换来的是每个模块多约 28% 的像素。只有在载荷大到「帧数会失控」时
（超过 `MAX_AUTO_FRAMES = 24`），密度才让位于帧数——等 30 帧比码密一点更糟。

这个改动只影响**显示方**：接收方的解码逻辑、喷泉码的语义、帧格式都没有变，
`NP1:<TYPE>:<seq>-<count>:<BASE32>` 一模一样。旧版本仍然能扫新版本的码，反之亦然。

## 小消息用**单张静态码**，不放动画

设备端实测：一台旧手机大约**每秒解码一次**（`已采样` 计数在十几秒里只涨到 18）。而插件端默认
每 420 毫秒换一帧——也就是每次尝试落在一张"已经换掉"的码上。用户看到的就是「18/0：采样了 18 帧，
一帧都没解出来」。这不是靠调参数能解决的：**尝试速度比码的变化速度慢**。

而一笔签名请求只有 315 字节，足以放进**一张**二维码：

| 消息 | 字节 | 单张码字符 | EC M | EC Q | EC H |
|---|---|---|---|---|---|
| 签名交易 | 315 | 535 | 77 模块 | **89 模块** | 97 模块 |
| 签名消息 | 196 | 345 | 61 | 69 | 81 |
| xpub 导出 | 476 | 794 | 89 | 105 | 121 |

手机离屏幕一臂距离、码占取景框 70% 时，1080 像素的取景里每模块约 **7–9 像素**——在实测的
"5 像素以上稳定读出"区间内。所以：

- 消息放得进一张码时，插件显示**单张静态码**（纠错等级 Q，比默认 M 更耐局部损坏）；
- 放不进时（例如带大结构体的 EIP-712）才退回动画；
- 动画模式保留一个按钮，码读不出来时可以手动切换；
- 动画超过 10 秒会**自动放慢**到每帧 900 毫秒——没有反向信道可以告诉插件端设备有多慢，
  所以这只能是对时间的猜测，而猜错的代价只是传得慢一点。

设备显示签名回执（NP-SIG）同理：签名很小，用单张静态码，插件端的摄像头随时可以拍。

接收方无需任何改动：`fragmentCount = 1` 的帧本来就是喷泉码的合法情形，一次扫描即可完成传输。
