# 安全模型

本文档说明 NetProof Wallet 的威胁模型、信任边界，以及**实现层面的已知弱点**。
原型代码未经安全审计，请勿用于保护真实资产。

---

## 1. 资产与对手

**要保护的资产**（按重要性）：

1. **助记词**（以及 BIP39 passphrase）——一旦泄露，资产即刻失守；
2. **签名权限**——诱使用户签一笔自己没看懂的交易，等价于泄露资产；
3. **隐私**——地址集合、余额、交易历史。

**对手模型：**

| 对手 | 能力 | 防御 |
|---|---|---|
| 恶意 dApp | 任意调用 `window.ethereum`、构造任意参数 | 设备独立展示解码后的真实内容；插件二次校验载荷 |
| 恶意/被攻破的浏览器环境 | 读取伴侣钱包存储、篡改其页面 | 存储里**只有 xpub**；签名必须经设备屏幕确认 |
| 对伴侣页面所在 origin 的 XSS | 读取 localStorage、伪造请求 | 只泄露地址；伪造的请求会在设备屏幕上显示真实内容 |
| 恶意 RPC 节点 | 返回伪造的 nonce/gas/余额/链 ID | nonce 与 gas 由节点提供**是已知弱点**（见 §4）；设备展示所有最终值 |
| 网络攻击者 | 观察/篡改一切网络流量 | 设备根本不联网；插件与 RPC 之间走 HTTPS |
| 物理接触设备的攻击者 | 拿到手机 | Argon2id（64 MiB / 3 轮）+ XChaCha20-Poly1305；无备份、无重置路径 |
| 摄像头旁的观察者 | 看到屏幕上的二维码 | 二维码只含公开信息（xpub、签名、请求），不含私钥 |
| 被污染的相机管线 | 提供低熵或可控的像素 | 熵**实测**而非假设；不达标则拒绝创建钱包 |

**明确不在威胁模型内：**

- 供应链攻击（npm 依赖、构建工具链）。这是所有 JS 钱包的共有弱点；
- 有 root 权限、能实时读写设备内存的攻击者；
- 用户自己把助记词抄到联网设备上（这是最常见的真实失守方式）。

## 2. 信任边界

```
┌─ 伴侣钱包 ─────────────────────┐   ┌─ 二维码 ─┐   ┌─ 离线设备 ────────────┐
│ 网页版 / 浏览器扩展             │   │ 公开信道 │   │ 信任：自己的摄像头像素  │
│ 不信任：dApp、页面、RPC 响应    │◀─▶│ 可被观察 │◀─▶│ 拥有：助记词、私钥      │
│ 不拥有：任何私钥               │   │ 可被替换 │   │ 能做的：签名、拒绝      │
│ 能做的：请求签名               │   └──────────┘   └──────────────────────┘
└──────────────────────────────┘                          ▲
        ▲                                                │ 用户的手指
        │ 扩展：window.ethereum (EIP-1193/EIP-6963)      │
        │ 网页：内置 dApp 测试台（同一套策略层）          屏幕上的内容
     dApp
```

**两种伴侣形态的取舍**（见 §4.11）：浏览器扩展能向 dApp 注入 `window.ethereum` 并被自动发现；
网页版不能注入，但**存储位置更糟**——它把 xpub 放在用户日常浏览的 origin 的 `localStorage` 里。
两者的共同点是决定性的：不持有任何私钥。

**设备是唯一的信任锚点。** 它不接受任何外部输入作为"事实"：
收到签名请求后，它自己解码 EIP-2718 载荷、自己计算签名哈希、自己展示解析结果、
再从**展示过的字段**重新序列化并签名。因此，插件被篡改的最坏后果是"用户看到一个
假的请求页面"——但设备屏幕上显示的是真的。

**但设备也不是全能的**：它不知道地址余额、不知道合约是不是恶意、不能模拟交易结果。
所以设备展示的是"这笔交易的字面含义"，不是"这笔交易会发生什么"。这是所有硬件钱包
（包括 Ledger/Trezor）的现状，也是为什么高风险操作要有醒目提示（无限授权、授权全部 NFT、
合约部署、未知 selector）。

## 3. 关键安全属性与实现位置

| 属性 | 实现 | 测试 |
|---|---|---|
| 伴侣钱包没有任何私钥 | `packages/companion` + 各宿主存储层只存 xpub | `companion.test.ts`、`store.test.ts` |
| 不实现本地签名兜底 | `packages/companion/src/rpc.ts`：签名方法一律排队等审批 | "never signs locally" |
| 设备签的就是它显示的 | `apps/hardware/src/screens/Sign.tsx`：审查与签名共用同一个解码对象 | `checkRequestAccount` + core 测试 |
| 响应必须绑定到请求 | `claim`（`packages/core/src/qr/protocol.ts`） | "binds a request to its exact bytes" |
| 插件独立校验签名 | `verifySignedTransaction` | "verifies a signed payload and detects a mismatch" |
| 熵不达标就不创建钱包 | `CameraNoiseCollector.finalize()` 抛错 | "refuses to create a wallet when…" |
| KDF 参数不可降级 | 保管库 AAD 覆盖 KDF 参数 | "refuses a KDF downgrade" |
| 设备无法联网 | Android 无 INTERNET 权限 + 页面 CSP | 人工检查 |
| 金额不会被四舍五入成 0 | `formatUnits` 保留有效位 | "formatting must never round to zero" |

整个 `packages/core` 中**不存在**任何"用本地随机数签名"或"用设备密码直接推导私钥"的代码路径。
这不是疏忽——那种兜底路径正是热钱包的失败模式。

## 4. 已知弱点（按严重程度）

### 4.1 `nonce` 和 gas 来自插件配置的 RPC 节点

设备离线，无法查询链状态，所以 nonce、gas limit、gas 价格、链 ID 全部由插件提供。
恶意节点可以：

- 提供一个**过高的 gas 价格**，让用户在不知情下多付手续费；
- 提供一个**过低的 gas limit**，使交易因 out-of-gas 失败但仍消耗 gas；
- 提供一个**过高的 nonce**，使交易长时间卡住。

**缓解**：所有最终值都显示在设备屏幕上（Gas 上限、Gas 价格、最大可能支出），
超过 500 Gwei 会有提示，用户可以选择换节点或拒绝。
**但不能完全防住**——用户必须自己判断 gas 是否合理。

**改进方向**：设备支持连接自建节点（但那就要联网，与空气隙矛盾）；
或由用户预先在设备上设置 gas 上限（白名单）。

### 4.2 熵管线的三个已修复缺陷（"点击完成采集没反应"）

用户报告：点击「完成采集，生成助记词」没有任何反应。根因是三个缺陷叠加，外加一个把失败藏起来的 UI 缺陷：

1. **去偏置跨空间配对。** von Neumann 要求配对的两个比特独立，而相邻像素因行/列读出偏移与 PRNU
   而相关，于是绝大多数比特对被判为"相同"并丢弃。改为**同一像素跨时间**配对后，可提取比特提高约 2.8 倍。
2. **对相关流跑 i.i.d. 检验。** 统计检验被直接施加在按光栅顺序排列的去偏置流上，
   `runs`、块频率、序列相关、MCV 在一台健康传感器上全部 p = 0，`finalize()` 直接抛错。
   现在检验跑在一份专门构造的抽样样本上（64 槽 × 每帧一比特、按帧奇偶分组以保证去偏置窗口不重叠）。
3. **样本随采集时长增长。** 固定 α 的假设检验随 n 增大必然拒绝：同一传感器采 40 帧通过、采 300 帧失败。
   即"采得越久越容易被拒绝"——完全反了。样本大小现在固定。

**外加 UI 缺陷**：错误信息渲染在页面顶部，而用户看的是粘在底部的按钮，中间隔着满屏的摄像头预览——
所以"失败"表现为"没反应"。错误现在显示在按钮旁边，并提供「重新采集」。

**教训**：安全机制的失败必须对用户可见，而且必须用与它所判定的假设一致的统计工具。
这次三条都写成了回归测试（`packages/core/test/entropy-realistic.test.ts`）。

### 4.3 熵估算基于启发式模型

`credit = 有效比特数 × 实测最小熵/比特 × 0.05` 里的 `0.05` 是**人为设定**的独立性折扣，
不是从物理模型推导出来的。它刻意保守，但仍然是假设。

**缓解**：NIST SP 800-22 风格的健康检验会拒绝统计性质异常的采集；达不到阈值就拒绝创建钱包。
**改进方向**：完整的 NIST SP 800-90B 熵源评估（需要实验室条件）。

### 4.4 相机预览管线可能降噪

如果手机的相机 HAL 在预览流上做时域降噪，可提取熵会暴跌。
设备会因此**拒绝创建钱包**（正确的失败方式），但也没有更好的办法从 WebView 里绕过它。

**缓解**：采集界面实时显示实测比特数；「设置与自检」展示完整的健康检验结果。

### 4.5 JS 无法保证内存擦除

助记词在解锁期间以 JavaScript 字符串形式存在于内存中。`lock()` 会丢掉引用并清空
passphrase 变量，但字符串内部数据何时被 GC 回收、是否被复制过，都无法控制。

**缓解**：解锁会话尽量短；锁定后不保留任何引用；设备不联网减少了内存被远程读取的途径。
**这是所有基于 JS 的钱包共同的限制**，包括 Electron 钱包。

### 4.6 保管库存在 WebView 的 localStorage

加密强度足够（Argon2id 64 MiB / 3 轮 + XChaCha20-Poly1305），但**密钥保护依赖设备密码的强度**，
没有硬件支持的密钥绑定。

**缓解**：接口（`apps/hardware/src/lib/storage.ts`）刻意做窄，便于换成
`@capacitor/preferences` + Android Keystore（硬件支持、可要求生物认证）。
设备密码有强度评估，且设备会提示密码强度不足。

### 4.7 服务 worker 生命周期

Chrome 会随时停止 Manifest V3 的 service worker。待审批请求持久化在
`chrome.storage.local`，但等待中的 Promise 在内存里；页面保持连接时端口会保活 worker。

**后果**：极端情况下，一个已排队但尚未批准的请求可能在 worker 重启后丢失，
用户需要重新发起。**不会**导致错误签名。

**改进方向**：为待审批请求实现一套显式的重连/恢复协议。

### 4.8 没有交易模拟

设备展示的是解码后的调用参数。对于未知合约调用，它只能提示"无法识别"。
一个精心构造的、参数看起来无害的调用仍可能造成损失。

**缓解**：未知 selector 醒目提示；无限授权/授权全部 NFT 标红；
`approve`、`transferFrom`、`setApprovalForAll` 等常见危险模式有专门解码。
**改进方向**：离线设备上做不了模拟；可以让插件提供模拟结果，但那就落入了"不信任输入"的禁区——
正确做法是在设备上内置一份常见合约/selector 数据库。

### 4.9 dApp 授权粒度是"账户级"

一旦用户批准某个站点，该站点可以读取全部导出账户的地址，并在**每次用户扫码确认**后请求签名。
它不能静默签名，但可以不断弹出请求骚扰用户。

**缓解**：授权列表可见且可撤销；每次签名都必须扫码（有物理成本，天然限流）。
**改进方向**：按账户粒度授权、按方法白名单（例如只允许 `personal_sign` 用于登录）。

### 4.10 导入的助记词无法被验证，只能被核对

导入用户提供的助记词时，设备只能验证 BIP39 **格式**（词表 + 校验位），
无法验证这是不是**你的**助记词。两个单词顺序对调仍可能通过校验位（概率约 1/16 的换位能通过），
抄错一个词且恰好通过校验也是可能的。结果是导入到一个**空钱包**，用户充值后才会发现资金丢失。

**缓解**（已实现）：
- 逐词校验并对词表外的单词给出拼写建议，明确区分"词表外"与"校验位不符"两种情况；
- 导入第二步强制显示派生出的**钱包指纹与第一个地址**，要求用户与原钱包逐位比对并显式勾选；
- 保管库把来源记为 `imported-mnemonic`，界面不会把导入的钱包说成摄像头生成的；
- 明确告知"如果这串词曾出现在联网设备上，应视为已泄露"。

**仍然存在的风险**：用户可以直接勾选"我核对过"而并不真的核对。这是无法用程序解决的问题，
只能在界面上把它讲清楚。**改进方向**：导入后要求完成一次小额签名验证，把"核对"从声明变成动作。

### 4.11 passphrase 与助记词共用同一个设备密码（产品决策）

按产品要求，passphrase 总是与助记词一起加密保存在保管库中，签名时自动使用，
不再提供"每次手动输入"的选项。

**代价（必须明确记录）**：两者由**同一个设备密码**保护。因此

- 保管库被攻破、设备被解锁、或设备密码被猜到/暴力破解 → 助记词与 passphrase **同时**泄露，
  钱包立即失守；
- passphrase **不再是独立的第二因子**。它仍然能防住"只有纸备份被看到"的场景
  （拿到 24 个词的人没有 passphrase 依然打不开），但防不住"设备被物理或软件攻破"。

**因此设备密码是唯一的防线**，强度要求相应提高：口令由 Argon2id（64 MiB / 3 轮）派生，
但 KDF 只能减缓暴力破解，不能替代一个足够长且唯一的密码。界面在创建时会说明这一点。

**回归到"独立因子"的改法**：`apps/hardware/src/state/session.tsx` 的 `persist()`
不再写入 `passphrase` 字段即可；`passphraseRequired` 这个非机密 flag 会保留，
所以解锁页仍会正确提示"你正在进入不带 passphrase 的钱包"。

### 4.12 插件看到的地址数量是隐私/可用性取舍

`eth_accounts` 返回"所有已导出账户 × 每个账户的派生地址数"（默认 20/账户，上限 200）。
派生得多，插件才能在多个地址上发现用户分散的资金；但同一个列表也会交给每个连接的 dApp，
从而**泄露钱包结构**：哪些地址属于同一个人、大概用过多少个地址。

**缓解**：数量可调小；设备侧可以选择只导出部分账户；未导出的账户对插件完全不可见。
**固有的部分**：只要插件要显示余额，它就必须把地址交给 RPC 节点，节点看到的更多。

### 4.13 样式工具类曾经让输入框完全无法使用（已修复）

助记词导入界面把只读展示用的 `.np-blur` 类加到了 `<textarea>` 上。
那个类里有 `pointer-events: none`——于是输入框**根本无法获得焦点**，
用户敲不进任何字，界面上的计数器始终显示"0 个单词"，而且不报任何错。

**修复**：
- `.np-blur` 不再包含 `pointer-events: none`（需要"死区"时改用显式的 `.np-blur--inert`）；
- 输入框不做任何模糊/遮蔽——要输入的东西必须可点、可读；
- 新增**源码级不变量测试**：断言 `.np-blur` 不得含 `pointer-events`，
  且任何 `<input>` / `<textarea>` 都不得带 `np-blur`（`apps/hardware/test/ui-invariants.test.ts`）。

**顺带修好的解析问题**：原先按单个空格切分，于是逗号分隔、带序号（`1. abandon 2. ability`）、
零宽空格等常见粘贴格式会被识别成 **1 个单词**（甚至看起来像 0 个）。现在支持逗号、中文逗号、
分号、竖线、制表符、换行、序号前缀、全角/不换行空格、零宽字符，并新增"识别到的单词"预览网格，
拼错的词会红框标出。

**教训**：样式工具类不应该悄悄移除交互能力；而"用户看不到任何错误"的失败模式，
比一个会报错的失败更难排查。两者现在都有测试守住。

### 4.14 本协议不与 BC-UR 互通

自研帧格式换来了可测试性，代价是无法与 Keystone / Sparrow / BlueWallet 等生态互通。
这只影响互操作性，不影响安全性。

### 4.15 网页版伴侣的存储位置不如扩展

网页版把 xpub 与设置放在 `localStorage`，而它所在的 origin 同时是你访问 dApp 的地方。
任何在这个 origin 上达成 XSS 的脚本都能读到这些数据。

**为什么仍然可以接受**：那里**没有**私钥、助记词、种子或密码（有测试断言这一点，
见 `apps/companion-web/test/store.test.ts`）。攻击者得到的是地址集合，以及"替用户排队一个签名请求"的能力——
而那个请求仍会完整地显示在离线设备的屏幕上，并在伴侣侧被三重校验。
换句话说，这个弱点的上限是**隐私**，不是资产。

**改进方向**：用扩展形态（存储与页面 origin 隔离）；或把网页版部署在一个用户不用于浏览 dApp 的独立域名上；
或改用非提取型密钥（WebAuthn/Passkey）包裹本地数据。

### 4.16 系统报告的网络状态可能不可信（已修复过一次误报）

早期版本在 `navigator.onLine === true` 时无条件弹出红色横幅要求开启飞行模式。
真机上即使用户已经开了飞行模式，横幅也不消失。

**原因**：Android WebView 通过 `ConnectivityManager` 推导 `navigator.onLine`，而**读取**连通性状态
需要 `ACCESS_NETWORK_STATE` 权限。当时的清单为了"干净"而刻意省略了这个权限，于是 WebView 无法注册
连通性回调，`onLine` 恒为 `true`。**是我自己的加固措施破坏了自己的检查。**

**修复**：不再由程序断言"你在联网"，改为展示三件可独立验证的事——
标注来源的系统状态、APK 缺少 INTERNET 权限这一事实（附自检命令）、以及用户本人的飞行模式确认记录。
同时补上 `ACCESS_NETWORK_STATE`（只读连通性查询，**不授予任何联网能力**），让那个状态通常是真的。

**教训（适用于所有安全 UX）**：钱包不能展示自己无法证实的断言。一个在用户做对了的时候还在报警的警告，
比不报警更糟——它训练用户忽略警告。这个教训已经写成测试：
`apps/hardware/test/network.test.ts` 断言 `online` 状态必须标注来源并披露权限失效模式。

### 4.17 网页版无法被 dApp 自动发现

网页不能向其它 origin 注入 `window.ethereum`。所以网页版没有 EIP-1193 provider，
dApp 无法通过 `window.ethereum` 或 EIP-6963 找到它。

**影响**：这是**功能性**限制而非安全问题。原型因此内置了「dApp 测试台」，
它直接调用与扩展完全相同的 `handleRpc` 策略层（同一个 `@netproof/companion` 包），
所以被检验的策略是真的，只有传输层不同。

**改进方向**：使用扩展形态，或将来支持 WalletConnect 一类的会话协议。

## 5. 审计清单

如果要评审这份代码，建议按以下顺序：

1. `packages/core/src/qr/protocol.ts` — `claim` 的构造与校验，以及 CBOR 的规范性；
2. `packages/companion/src/rpc.ts` — 方法分类（转发 / 拒绝 / 排队）是否有遗漏；
3. `packages/core/src/entropy/collector.ts` — 熵估算公式与 `blockingReasons()` 的门槛；
4. `apps/hardware/src/screens/Sign.tsx` — 审查与签名是否共用同一份解码结果；
5. `apps/companion-web/src/screens/Sign.tsx` 的 `finish`（以及扩展里对应的 `finishApproval`）
   — 三项校验是否都不可绕过；
6. `apps/extension/src/content/inject.ts` — provider 是否可能被页面劫持或覆盖；
7. `packages/core/src/vault/vault.ts` — AAD 覆盖范围是否完整。

配套测试文件与上述模块一一对应，建议先读测试再看实现——测试表达的是**意图**。
